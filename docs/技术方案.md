# ProcBeat 技术方案

> 面向维护者的设计文档：为什么这么实现、每个数字的口径从哪来、换环境时该改哪里。
> 只看面板怎么用，去 `docs/用户手册.md`。

- 项目位置：`/home/admin/workspace/monitor/`
- 首次上线：2026-09-28
- 目标机器：Ubuntu 22.04.5 / 内核 5.15.0-142 / 2 核 / 1.6 GiB 内存 / 40 GiB 根分区

---

## 1. 背景与目标

这台机器上跑着 qodercn 服务和 nginx 站点，此前**没有任何监控手段**：出现卡顿、内存打满、
磁盘写爆时，事后无从查证是几点发生的、持续多久、当时哪台负载高。

目标是一个**手机浏览器点开即用**的仪表盘，展示当前值与 7 天历史。

### 明确不做的（需求确认时排除）

| 排除项 | 原因 |
|---|---|
| 网络流量 | `/proc/net/dev` 可做，但需要额外的差值与多网卡聚合逻辑，当期不需要 |
| PSI 压力指标（`/proc/pressure/*`） | 内核 5.15 有，但解读门槛高，不适合"点开即用" |
| 进程 Top-N | 会把"哪个进程在吃内存"这类敏感信息暴露到无鉴权页面上 |
| 服务存活探测 | 属于告警系统，不是指标面板；且需要维护进程清单 |
| 温度 | 实测 `/sys/class/thermal/` 下只有 `cooling_device*`，无 `thermal_zone*`，采不到 |
| 鉴权 / 多用户 | 见 §11，是已知风险而非遗漏 |

## 2. 环境实测约束

方案里几个看起来"过度讲究"的地方，都来自这几条实测结论。

### 2.1 `NODE_OPTIONS` 是有毒的

登录 shell 导出了 `NODE_OPTIONS="--max-old-space-size=8192 --use-system-ca"`，本机 node
直接拒绝执行任何东西——`node -v` 都会失败：

```
$ node -v
node: --use-system-ca is not allowed in NODE_OPTIONS
```

即使去掉 `--use-system-ca`，`--max-old-space-size=8192` 在 1.6 GiB 的机器上也是有害的
（堆上限远超物理内存，一旦真用满就是 OOM killer 来收拾）。

**对策**：`monitor.sh` 启动前 `export NODE_OPTIONS="--max-old-space-size=96"`，
systemd unit 里再用 `Environment=` 写一遍。两处都要，因为 unit 不继承 shell 环境，
而手工跑 `monitor.sh` 时不经过 systemd。

### 2.2 没有可复用的存储与工具

`sqlite3` 二进制不存在、python `psutil` 不存在、`systemctl --user` 不可用（无 bus，
连不上 `users/1000.slice`）。可用的只有 `sudo systemctl`（系统级）。

**对策**：存储用按天分文件的 JSONL，追加写；服务用系统级 unit。

### 2.3 nginx 的 location 优先级陷阱（决定性）

`/etc/nginx/sites-available/default` 里已有兜底块：

```nginx
location ~* \.(js|css|json|map|txt|xml|ico|png|jpe?g|gif|webp|avif|svg|woff2?|mp3|ogg|wav|webm|m4a)$ {
    try_files $uri =404;
}
```

nginx 的匹配顺序是 **精确 `=` → 最长前缀 →（未被 `^~` 截断时）正则 → 前缀**。
所以写成普通前缀 `location /monitor/` 时，`/monitor/app.js` 会**先命中那条正则**，
被拿去站点仓库的 `root` 下找文件 → 404，面板只剩白屏。

**对策**：必须写 `location ^~ /monitor/`，`^~` 会让 nginx 在前缀命中后跳过正则检查。
这条是在一台一次性 nginx（端口 8080、独立 prefix）上复现并验证的，没拿生产配置试错。

### 2.4 `proxy_pass` 的尾部斜杠

```nginx
proxy_pass http://127.0.0.1:3000/;   # 带 URI 部分
```

带 `/` 才会把 `/monitor/api/current` 重写成 `/api/current`；不带则前缀原样透传，
Node 侧全部 404。

### 2.5 其他

- `fs.statfsSync('/')` 可用，返回 `bsize/blocks/bfree/bavail`，与 `df` 同源。
- `/proc/diskstats` 里分区行（`vda3`）是整盘行（`vda`）的子集，取分区会和整盘重复计数。
- 前端资源必须用**相对路径**（`./app.js`），因为面板部署在子路径 `/monitor/` 下；
  同时不改 `<base>`，保证直连 `127.0.0.1:3000` 也能用。

## 3. 总体架构

```
                     ┌─────────────────────── 单进程 Node（无依赖）───────────────────────┐
 /proc/stat          │  Sampler            Store                       http.Server        │
 /proc/meminfo ─────►│  sample(span) ─┬──► │  append(rec) ─► data/raw/YYYY-MM-DD.jsonl    │
 /proc/loadavg       │  纯读，算差值   │    │             └─► 每分钟折叠 ─► data/agg/...   │──► 127.0.0.1:3000
 /proc/diskstats     │                └──► │  内存只留 latest 一份        history() 抽稀    │
 statfs("/")         │  5 秒一次 tick      │  prune() 每 6 小时          读 public/*       │
                     └────────────────────────────────────────────────────────────────────┘
                                              ▲                                    │
                                              │ nginx:80                            ▼
                                     /monitor/ ──反代──► 手机浏览器（5 秒轮询 + Canvas）
```

模块划分（每个文件单一职责，可独立测试）：

| 文件 | 职责 | 不做的事 |
|---|---|---|
| `sampler.js` | 读 `/proc` 与 statfs，算差值 | 不写文件、不依赖前一个样本之外的状态 |
| `store.js` | 落盘、聚合、淘汰、抽稀查询 | 不读 `/proc`、不起服务 |
| `server.js` | 定时器 + HTTP 路由 + 静态文件 | 不算指标 |
| `public/app.js` | 轮询 + Canvas 绘图 | 不聚合、不做阈值判断以外的逻辑 |
| `selftest.js` | 合成 `/proc` 夹具验证采集算法 | 不碰真机负载 |
| `seed.js` | 合成 7 天历史，验证降采样查询路径 | 不参与运行期 |

`Sampler` 的构造参数 `{ procDir, mountPoint }` 可注入，这是"能在 2 核机器上确定性地
测 CPU 差值算法"的关键——不需要真的把机器压满。

## 4. 指标采集口径

### 4.1 CPU

**数据源**：`/proc/stat` 的 `cpu` 汇总行与 `cpuN` 每核行，字段顺序
`user nice system idle iowait irq softirq steal guest guest_nice`。

**算法**：jiffy 是累计值，必须两次采样求差：

```
busy = (user + nice + system + irq + softirq + steal) 的差值
total = (上面 6 项 + idle + iowait) 的差值
占用% = busy / total × 100
```

三个容易算错的点，`selftest.js` 里都有对应断言：

1. **`guest`/`guest_nice` 不参与求和**。内核已经把 guest 时间并入 `user`/`nice`，
   再加一次会算出 >100% 的值。求和只取前 8 个字段。
2. **`steal` 计入忙碌，`iowait` 计入空闲**。steal 是虚拟机上被宿主拿走的时间，本机
   无法干预，但确实是用户感受到的不可用；iowait 是 CPU 空闲且在等 IO，算忙碌会让
   "CPU 100%"失去意义。
3. **核数变化要作废旧基准**。CPU 热插拔或读取到不完整的一帧时，新旧样本的核数不一致，
   差值会错位——检测到行数变化就把 `prevCpu` 置空，重新预热一次。

**首帧语义**：第一次调用只建立基准、返回 `null`，所以服务启动后约 5 秒内
`/api/current` 是 `503 {"error":"warming up"}`。这是刻意设计，不能返回 0 冒充读数。

### 4.2 内存

```
used = MemTotal − MemAvailable
```

**不用** `free` 的 `used` 口径（= total − free − buffers − cache）。Linux 3.14 起
`MemAvailable` 是内核自己估的"不触发交换前能给了新进程的量"，比手工扣减准确；
页缓存随时可回收，把它算成"已用"会长期虚高。结果就是**面板的内存占用比 `free` 显示的高**，
这是口径差异不是 bug（见 §10 实测对表）。

### 4.3 负载

`/proc/loadavg` 前三个字段（1/5/15 分钟）。读它顺带能证明 `/proc` 整体可读——如果
只有 loadavg 有值而 CPU 为空，就知道是 CPU 那步出了问题。

### 4.4 磁盘容量

`fs.statfsSync('/')`，并**与 `df` 完全同口径**：

```
已用 = (blocks − bfree) × bsize
可用 = bavail × bsize          ← 不是 bfree
使用率 = 已用 / (已用 + 可用)
```

用 `bavail` 而不是 `bfree`，是因为 ext4 默认给 root 预留 5% 空间。按 `bfree` 算会把
预留块算进"可用"，导致日常用户视角的剩余量偏大（实测 17% vs 20.5% 的差就是这么来的）。

`df` 的百分比向上取整，这里保留一位小数，所以 `df` 显示 17% 时面板显示 16.4%～16.6%。

### 4.5 磁盘 IO

**数据源**：`/proc/diskstats`，字段 `reads completed reads_merged sectors_read ms_read writes ...`。

- **设备名从 mountinfo 反推整盘**：`/proc/self/mountinfo` 里取 `/`（或 `/mnt`）行的
  mount source（`/dev/vda3`），再用 `base.replace(/p?\d+$/, '')` 去掉分区号得到 `vda`。
  `nvme0n1p3 → nvme0n1` 这类带 `p` 的分区名也覆盖；`md0` 这种去尾号后不存在的设备，
  退化成用分区自身的行。
- **不做设备白名单**：`io()` 只查那一个反推出来的名字，`loop*`/`ram*` 之类天然不会参与，
  不需要按前缀过滤。找不到对应行就返回 `null`（这一拍没有 IO 数据，而不是报 0）。
- **扇区一律按 512 字节算**。内核文档明确规定 `diskstats` 里的扇区计数与逻辑扇区大小无关，
  恒为 512B，乘 `statfs` 的 `bsize` 是错的。
- 速率 = 差值 / `span`，`iops = (reads + writes) 差值 / 秒`。
- `loop*`、`ram*` 等虚拟设备不参与（只认反推出来的那一个名字）。

### 4.6 采样窗口

采样周期 5 秒，`span = now - lastTick` 随每次采样一起记录。事件循环被拖长时窗口跟着变宽，
读数变成"更长一段时间的平均值"——`/api/current` 里的 `span` 就是为了让这种情况看得出来。
实测节奏：min 4999 / p50 5004 / p95 5006 ms。

## 5. 存储设计

### 5.1 两层保留

```
data/raw/YYYY-MM-DD.jsonl    5 秒原始点，保留今天 + 昨天（rawKeepDays=1）
data/agg/YYYY-MM-DD.jsonl    1 分钟聚合，保留 7 天（aggKeepDays=7）
```

日期用**东八区**（`new Date(ms + 8h).toISOString().slice(0,10)`），文件名和 `ls`、和人的
直觉对齐，不然 UTC 分界会让"今天的日志"在早 8 点前指向昨天。

容量按实测行均字节算：

| 层 | 行均 | 每天行数 | 每天体积 | 保留 | 稳态 |
|---|---|---|---|---|---|
| raw | 205 B | 17 280 | 3.5 MB | 2 个日文件 | ≈ 7 MB |
| agg | 236 B | 1 440 | 0.34 MB | 8 个日文件 | ≈ 2.7 MB |

**稳态合计 ≈ 10 MB**，且天然有界——不是靠"定期清理旧数据"维持，而是文件按天命名 +
按日期字符串比较淘汰（`prune()` 每 6 小时一次，启动时也来一次）。

### 5.2 记录格式（字段压短以省体积）

原始行（取自实机 `data/raw/2026-09-28.jsonl`）：

```json
{"t":1790589265961,"cpu":9.3,"cores":[7.7,10.9],
 "mu":1200701440,"ma":486375424,"mt":1687076864,"l":[0.32,0.28,0.21],
 "dp":16.5,"du":6579642368,"da":33367564288,"dt":41882943488,
 "ri":0.11,"wi":0.11,"iops":11.2}
```

聚合行（实机，12 个样本折成一行）：

```json
{"t":1790589180000,"n":12,"cpu":9.85,"cpuMax":23.2,
 "mu":1207951019,"muMax":1236848640,"ma":450228224,"mt":1687076864,
 "l":[0.358,0.272,0.208],"dp":16.5,"du":6579269632,"da":33367937024,"dt":41882943488,
 "ri":4.237,"wi":0.096,"iops":112.7}
```

`cpu` 是 12 个样本的均值，而 `cpuMax=23.2` 说明这一分钟里有个 5 秒窗口冲到了 23%——
这正是 1 分钟视图需要峰值线的原因：光看均值会把这种短尖峰完全藏起来。

字段字典：`t` 时间戳(ms)、`cpu` CPU%、`cores` 每核%、`mu/ma/mt` 内存 已用/可用/总量(B)、
`l` 1/5/15 分钟负载、`dp/du/da/dt` 磁盘 使用率%/已用/可用/总量(B)、
`ri/wi` 读/写 MB/s、`iops` 次/秒、`n` 该分钟参与的样本数、`*Max` 该分钟峰值、
`ma` 在聚合里取的是**最小可用**（最紧张的那一刻），不是平均。

### 5.3 写入的正确性细节

- **单行 `appendFileSync`**。一行 200 多字节，远小于 4096B，对单写者来说 write(2) 是
  原子的：进程崩了最多丢一行，不会出现半行毁掉整个文件。读侧仍对 `JSON.parse` 失败
  的行 `continue`，双保险。
- **聚合桶在内存里累加，跨分钟时才落盘**。内存里只保留"上一个原始样本 + 当前分钟的桶"，
  **没有任何无界数组**。
- **`flushedUntil` 防重启后重复聚合**。上次退出时已写过的最后一分钟记在 `flushedUntil`
  （启动时从 agg 目录倒读最后一行的 `t` 得到）。重启后若又从同一分钟采样，直接聚合会
  写出第二条同 `t` 的记录，查询时挑到哪一条全看目录返回顺序。实测：跨分钟边界重启，
  agg 从 57 行 → 58 行、58 个唯一分钟，没有重复。
- **IO 用 `ioN` 而不是 `n` 做分母**。`s.io` 只在 diskstats 读成功的那些 tick 上存在，
  除以总 tick 数会把速率摊薄。
- **SIGTERM/SIGINT 时 `store.flush()`**，把当前未满一分钟的桶先落盘，避免整段丢掉。

## 6. 查询与抽稀

**约束**：手机可视宽度约 400 px，每条序列**最多 240 个点**，再多只是浪费带宽和 CPU。

步长阶梯：

```
[5, 10, 15, 30, 60, 120, 300, 600, 900, 1800, 3600, 7200, 21600]（秒）
```

选取规则是 `STEPS.find(s => window/s + 1 <= 240)`，`+1` 是因为首尾各占一格——少了这个
`+1` 就会算出 241 点，正好越界（这个 bug 出现过并被测出来）。

实测各档（用 `seed.js` 灌满 24h 原始 + 8d 聚合后查询）：

| range | source | step | 点数 | 最大响应 |
|---|---|---|---|---|
| 1h | raw | 30 s | 121 | ≈ 7.7 KB（含每核 3 条序列） |
| 6h | agg | 120 s | 181 | ≈ 10 KB |
| 24h | agg | 600 s | 145 | ≈ 10.5 KB |
| 7d | agg | 3600 s | 169 | ≈ 10.6 KB |

**数据源路由**：只有 `1h` 读原始，`6h/24h/7d` 一律读聚合。理由是每核曲线只有 1h 视图
需要 5 秒粒度，其他窗口读聚合既快又不会损失可读信息；`7d` 读 raw 要扫 17000 多行，
在 2 核机器上是纯浪费。

**桶内聚合而非取最后一个点**：24 小时视图里每 10 分钟取一个瞬时值，会把尖峰整个抹掉。
`scan()` 因此按桶累加（`MEAN` 字段求均值、`PEAK` 字段取最大、每核求均值），`t` 用桶内
最后一个样本的时间戳（点画在桶右端，语义是"截至这一刻"）。

**读文件的方式**：分块 `readSync`（64 KiB）+ 行尾残留拼接，边读边解析，
禁止 `readFileSync` 整个日志文件（否则一次查询就能制造几 MB 的大字符串，把堆顶起来）。
`fastTime()` 先只看行首的 `"t":` 手工取时间戳，窗口外的行直接跳过，不用付 `JSON.parse` 的钱。

## 7. API 契约

只监听 `127.0.0.1:3000`，无鉴权，所有响应带 `Cache-Control: no-store`。

### `GET /api/current`

最新一次采样。首次采样完成前返回 `503 {"error":"warming up","interval":5000}`。

```json
{"t":1790587423000,
 "cpu":{"total":6.4,"cores":[6.3,7.6]},
 "mem":{"total":1687076864,"used":1184927744,"avail":502149120},
 "load":[0.49,0.26,0.18],
 "disk":{"total":41882943488,"used":6566879232,"avail":33380327424,"pct":16.4},
 "io":{"rMBs":0,"wMBs":0.06,"iops":3.2},
 "span":5003,"uptime":14,"interval":5000}
```

`span` 是本次 cpu/io 所覆盖的毫秒窗口；`uptime` 是进程存活秒数（判断"是不是刚重启过"）。

### `GET /api/history?range=&metric=`

- `range`：`1h`（默认）| `6h` | `24h` | `7d`，非法值 → `400`
- `metric`：`cpu`（默认）| `mem` | `load` | `disk` | `io`，未知值 → 返回空 `series` + `empty:true`（不是 400，方便前端并发拉取时不因一个指标名拖垮整屏）

```json
{"metric":"cpu","range":"7d","step":3600,"source":"agg",
 "series":[{"name":"CPU","unit":"%","points":[[1790000000000,12.5],...]},
           {"name":"峰值","unit":"%","points":[...]}]}
```

约定：

- `points` 里的值为 `null` 表示该桶无数据，前端断线处理（不画成 0）。
- `峰值` 序列只在 `source === "agg"` 时存在。5 秒原始点本身就能体现尖峰，不需要再算分钟最大值。
- 每核序列 `cpu0/cpu1/...` 只在 `range === "1h"` 时给出。7 天里核数可能变化，混着画没意义。
- 非 `GET`/`HEAD` 一律 `405`（此前会返回 200，已修）。

## 8. 前端设计

**零构建**：手写 HTML + Canvas + 原生 ESM-free 脚本。2 核 / 可用 620 MB 的机器上不起
打包工具链，也不需要。

### 轮询而不是 SSE

| | 5 秒轮询 | SSE |
|---|---|---|
| nginx 侧改动 | 无 | 要关 `proxy_buffering`、调 `proxy_read_timeout`，改共享生产配置 |
| 手机切后台/休眠 | 自动停（`visibilitychange` 里暂停，回来立刻补一次） | 静默断流，需要重连逻辑 |
| 延迟收益 | 采样本身就是 5 秒一次，SSE 换不来任何"更快" | — |

采样周期 = 轮询周期时，SSE 只是多一套要维护的失败模式。所以：**轮询**。

### 刷新节奏

- 数字卡片：每 5 秒（跟着 `/api/current`）。
- 历史曲线：每 6 次轮询一次（≈30 秒），切时间范围时立刻刷。一次全刷要扫 5 个指标的日志
  文件，在 2 核机器上跟着 5 秒轮询跑纯属浪费。
- 首屏第一次轮询就强制刷历史（`state.ticks === 1`），否则图表要空白 30 秒。

### Canvas

- 按 `devicePixelRatio` 放大画布再缩小显示，否则手机上曲线是糊的。
- **`height` 只能由调用方传进来**。`canvas.height` 是反射属性，写回去会同时改掉 HTML
  `height` 属性；下次再从属性读基准值，就把已放大的值当原始值——dpr=3 时高度每轮翻三倍，
  几次重绘就把页面撑爆。这个 bug 出现过，修复方式是把高度常量放进 `CHARTS[*].opts.height`。
- 一个可复用的 `drawLine()`；x 轴只画 4 个刻度（手机宽度画 6 个就挤了）。
- 图例用 `createElement`/`createTextNode` 构建，**不用 `innerHTML`**（内容来自 API，
  虽然是自己产的，但不给 XSS 留口子）。

### 纵轴边界：百分比图钉死 0–100

`drawChart` 的 `opts` 里 `fixedMax` 是给百分比类指标（CPU%、磁盘%）用的，它同时决定两件事：

```js
if (opts.fixedMax !== undefined) {
  hi = opts.fixedMax;   // 上限就是 100，不参与自适应
  lo = 0;
} else {
  lo = Math.min(lo, 0);
  if (hi === lo) hi = lo + 1;
  const pad = (hi - lo) * 0.08;
  hi += pad;                       // 非百分比图才留 8% 呼吸空间
  if (!opts.zeroBase) lo -= pad;
}
```

两条各自的理由：

- **上限不能加留白**。早期版本对所有人一律 `hi += (hi-lo)*0.08`，于是 CPU 长期 100% 时
  顶部刻度标出 **108%**——一个不存在的数值，看着像图表坏了。百分比的天花板是定义，
  不是数据特征，没有"超出上限"可言。
- **下限不能自适应**。同样不能给小波动拉满画幅：CPU 一直在 3% 附近抖，若按数据范围缩放，
  那点抖动会占满整张图，看着像出了大事。所以 `fixedMax` 序列**既不放大也不缩小**，
  永远画在 0–100 的尺子上，读者拿任意两天的图对比能得到一致的结论。

真出现越界的脏数据（比如采样差值算出 130），曲线在 `Y()` 里被 `Math.max(lo, Math.min(hi, v))`
裁到顶线，**刻度不外溢**、图不撑坏。`selftest`/无浏览器场景下这条逻辑用 `node:vm` 加载真实
`app.js`、stub 掉 canvas，捕获 `fillText` 的 y 轴标签断言——130% 脏数据和全零数据下都稳定输出
`0 / 33.3 / 66.7 / 100`。

内存、负载、IO 不是百分比，仍走自适应（`zeroBase` 只保证不从负数或半空画起）。

### 主题与安装

- 深色跟随 `prefers-color-scheme`，用 CSS 自定义变量 + `<meta theme-color>` 两套；
  不做手动切换按钮（多一个状态要存、要和图表重绘联动，收益低）。
- `color-mix()` 带 `var(--bg)` 兜底写法，老浏览器不至于变成透明。
- 有 `manifest.webmanifest`（`display: standalone`，可加到主屏）。
  **刻意没有 service worker**：缓存型 SW 一旦在手机上上线，很难远程清掉——
  它会持续用旧版 `app.js`，而这个面板根本没有离线需求。

## 9. 部署与 nginx 接入

### 9.1 进程管理

`monitor.service`（系统级 unit，因为 `systemctl --user` 在这台机器上不可用）：

```ini
[Service]
User=admin
Group=admin
WorkingDirectory=/home/admin/workspace/monitor
ExecStart=/usr/bin/node /home/admin/workspace/monitor/server.js
Environment=NODE_OPTIONS=--max-old-space-size=96
Environment=MONITOR_HOST=127.0.0.1
Environment=MONITOR_PORT=3000
Environment=MONITOR_INTERVAL=5000
Restart=always
RestartSec=3
MemoryMax=200M
TasksMax=64
NoNewPrivileges=true
ProtectSystem=full
PrivateTmp=true
ReadWritePaths=/home/admin/workspace/monitor/data
# [Install] WantedBy=multi-user.target
```

`ProtectSystem=full` 把 `/usr`、`/boot`、`/etc` 挂成只读，因此 `ReadWritePaths` 必须
显式放行 `data/`。`MemoryMax=200M` 是硬墙，防止哪天内存泄漏把整台机器拖死——监控进程
不该比被监控的服务更危险。

实测：`Restart=always` 生效，`NRestarts=0`；cgroup `memory.current` ≈ 12.7 MB，
进程 RSS ≈ 36～45 MB（RSS 含 node 二进制与共享库映射，两个数口径不同）。

`monitor.sh` 提供 `install|start|stop|restart|status|logs|selftest`。装了 unit 就走
`systemctl`，没装退化成 `nohup + pidfile`，方便"先试跑再正式接管"。

### 9.2 nginx：drop-in 目录，谁也不改谁的文件

`/monitor/` 的路由定义住在 **`/etc/nginx/snippets/servers/monitor.conf`**（唯一事实来源），
站点配置里只有一行**通配** include：

```nginx
include /etc/nginx/snippets/servers/*.conf;
```

为什么要拆到这个程度：站点仓库的 `deploy.sh` 每次发布都会用它自己的模板
**整体覆盖** `/etc/nginx/sites-available/default`，把 location 写进线上文件，下次别人发布就没了。

早期版本是让 `deploy/nginx-apply.sh` 一次改**两处**——线上配置 + `站点仓库/deploy/nginx-site.conf`
模板。这确实是解决了"被覆盖"，但代价是两个仓库互相改写对方的文件：monitor 的一次执行会让
站点仓库的工作树莫名变脏，站点仓库更新一次模板又可能顺手把那行 include 删掉，
而且路由这件事被提交进了另一个项目的 git 历史。

现在是 drop-in：

- `nginx-apply.sh` 只做一件事——把片段装到 `/etc/nginx/snippets/servers/monitor.conf`，
  然后 `nginx -t` → reload → 自检。**不写线上配置，不写任何别的仓库。**
-站点仓库的模板常驻那行通配 include，它不需要知道 monitor 存在。
- 通配 include 在目录为空、甚至目录不存在时都能通过 `nginx -t`（已实测），所以这行可以永久常驻。

片段内容：

```nginx
location = /monitor     { return 301 /monitor/; }
location ^~ /monitor/   { proxy_pass http://127.0.0.1:3000/; ... }
```

`^~` 与尾部 `/` 的必要性见 §2.3、§2.4。

**`nginx-apply.sh` 的四条不变式**（都是这轮 review 里补上的，不是设计之初就想到的）：

1. **所有只读前置检查排在第一次写盘之前**。曾经发生过：脚本先把片段装进
   `servers/monitor.conf`、并顺手移走旧布局的残留文件，然后才检查站点里有没有那行通配
   include——一检查不过直接 `exit 1`，于是线上留下一个没人加载的孤儿片段，而旧片段已经被
   搬走了。现在顺序是：读站点 → 查通配 include → 查重复 include → 才开始写。
2. **拒绝"通配 + 点名"双 include**。如果站点里既有 `include .../servers/*.conf;` 又有一行
   `include /etc/nginx/snippets/servers/monitor.conf;`（老版本留下的），同一份片段被加载两次，
   `location ^~ /monitor/` 重复定义，`nginx -t` 直接失败——而这会连带**整台机器的 nginx 配置**
   一起校验不过。所以脚本在写盘前先 grep 点名 include，发现就退出并说明怎么修。
3. **片段属主必须是 `root`**。`cp -a` 会保留源文件的 `admin` 属主。这个目录是所有服务往 nginx
   里塞 location 的公共入口，任何 admin 进程免 sudo 就能改它，等于任何 admin 进程都能改写
   这台机器的路由。装完立刻 `chown root:root` + `chmod 644`。
4. **不写线上配置，不写任何别的仓库**。这一条从第一版就成立，也是 drop-in 相对"改两处"的
   核心收益。

**以后新增项目**：往那个目录里丢一个以自己命名的片段文件即可，不需要跟任何已有项目协调，
也不需要改任何人的模板——nginx 的前缀 location 按最长匹配而非文件顺序，多个 drop-in 之间
没有加载顺序问题（这是它比 Apache 的 `Include` 省心之处）。唯一不要做的是把 location
抄进多个模板——片段只有一份，改一处生效。

### 9.3 reload 后自检为什么要重试

`nginx -t` 通过、reload 成功，紧接着 `curl` 却可能读到**旧配置**的行为：旧 worker 还会把
手头连接答完。站点仓库的 `deploy.sh` 早就踩过这个坑（它用 `__deploy_probe__` 返回
发布 ID 来规避）。`nginx-apply.sh` 的 `check()` 因此对每项断言最多重试 10 次、间隔 0.5 s。
这个重试逻辑是实测逼出来的：第一次跑自检时 3 项 FAIL、且值恰好是"期望带引号"，
两个 bug（旧 worker + `$(...)` 里引号被当字面量）一起暴露。

### 9.4 drop-in 目录的代价（如实记录）

`/etc/nginx/snippets/servers/` 是**约定**，不是 nginx 的原生机制，代价有三条：

- 它是一次"跨仓库的隐形接口"：monitor 依赖站点仓库的模板保留那行通配 include。
  模板里已写了注释禁止别的服务改这个文件，但注释拦不住误删——真删了，`nginx-apply.sh`
  会检查失败并明确报出原因，不会静默把路由装到没人加载的地方。
- 目录里任何一片写坏，`nginx -t` 整站失败，**所有服务一起不可用**。这是共享生产配置的固有
  风险，与 drop-in 无关；缓解手段是 apply 脚本在 `nginx -t` 失败时回滚片段再退出。
- 反向耦合也存在，而且比上面那条更隐蔽：站点仓库的 `deploy.sh:113` 会把**它自己的模板**
  include 进一个临时 `http{}` 里做发布前语法预检，而模板那行通配 include 会把
  `snippets/servers/*.conf` 一起收进来——**monitor 的片段一旦写坏，别人家的发布预检就红**。
  已实测：现在带着 monitor 片段跑它那套临时配置，`nginx -t` 通过。这条决定了
  monitor 的片段必须与仓库里的 `deploy/monitor-snippet.conf` 保持同步、且 apply 脚本必须
  带 `nginx -t` 门禁，不能"手工编辑线上那份先看效果"。
- 片段只装不卸：`nginx-apply.sh` 没有对应的 remove 命令。卸载要手工 `rm` 那个片段再 reload；
  顺序上先摘路由再停服务，反了会在 nginx 里留一段 502 时间（详见用户手册 §7）。

## 11. 健壮性与安全

**进程不被单点异常带走**（这条是复审里最高优先级的一条，全部已落地）：

- `http.createServer` 的回调整体包 try/catch → 任何抛出转成 500，而不是 uncaughtException
  退进程。触发条件很朴素：畸形 `Host` 让 `new URL()` 同步抛错。
- `req.headers.host` 先过 `/^[\w.-]+(:\d{1,5})?$/` 再进 `new URL`。
- `tick()` 里 `sampler.sample()`、`store.append()`、`prune()` 各自包 try/catch：
  `/proc` 读不到、磁盘写满、目录被删，都不该让服务消失。
- `lastTick` 在采样**之前**更新：否则一次抛错会让下一次窗口累积成几分钟，读数失真。
- `store` 的 `readdirSync` 全部包 try/catch（`ProtectSystem` 或人为误删不该致崩）。

**无状态服务**：进程不持有任何不能从磁盘恢复的状态；重启只丢当前未满一分钟的聚合桶
（且在 SIGTERM 时会主动 flush）。

**安全面**：

- 只监听 `127.0.0.1`，对外只经 nginx:80 暴露 `/monitor/` 一个前缀。
- 静态文件只服务 `public/` 下真实存在、且后缀在白名单里的文件。防越界有三道：
  `new URL()` 会把 `..` 归一化掉（实测 `--path-as-is`、裸 socket 原始路径、`%2e%2e%2f`
  三种写法都拿不到 `public/` 外的文件）；`path.resolve` 后再校验 `startsWith(PUBLIC_DIR + sep)`
  作为第二道；后缀白名单是第三道。`Cache-Control: no-store` 避免中间代理缓存住一份旧面板。
  注意 `serveStatic` **不做 `decodeURIComponent`**，所以带百分号编码的路径会原样拼进
  `path.resolve`，指向一个不存在的文件——这同时也意味着含空格/中文的文件名取不到，
  `public/` 下保持纯 ASCII 命名是前提。
- 只读方法：非 `GET`/`HEAD` → 405。
- systemd 侧 `NoNewPrivileges` + `ProtectSystem=full` + `PrivateTmp` + `TasksMax=64`，
  被攻陷时的可用爆炸半径限制在 `data/` 目录的写权限内。
- **未做鉴权，是已知风险**。当前只暴露 CPU/内存/负载/磁盘曲线，敏感度低；但"这台机器
  现在空闲"本身就是信息（可被用来挑时机探测）。任何需要登录/进程/网络明细的扩展，
  **必须**先加 Basic Auth 或 IP 白名单。

## 12. 已知限制

1. **无鉴权**（见上）。
2. **无温度**：硬件上没有 `thermal_zone*`。
3. **单机、单实例、无高可用**：面板本身挂了就没有监控。这是"监控被监控者"的固有局限，
   要突破得引入外部拨测。
4. **采样窗口 = 定时器间隔**。事件循环被拖长时窗口跟着变宽，读数变成一段时间的平均值；
   `span` 字段如实反映，但曲线不会为此重算。
5. **重启会丢掉未满一分钟的聚合**（SIGTERM 会 flush，`kill -9` 或 OOM 不会）。
6. **每核序列在 1h 视图按 `cpuN` 顺序画**，不感知核的"身份"变化；热插拔后图例编号会错位。
7. **磁盘只有一个挂载点**（`/`）。要监控数据盘得给 `Sampler` 加多挂载点支持。
8. **JSONL 不是数据库**：没有任意维度查询、没有告警、没有跨机聚合。需要更长历史或
   多机对比时，应该整体迁到 Prometheus + node_exporter，本项目里只有 `sampler.js` 的
   口径讨论可以复用。

## 13. 演进方向（如果还要做）

按"代价 / 收益"排序，不是待办清单：

1. **加 Basic Auth**（1 行 nginx `auth_basic` + 一个 `htpasswd`）——把 §11 的已知风险关掉。
2. **磁盘扩展到多挂载点**：`Sampler` 收一个挂载点数组，`store` 记录里加 `mnt` 维度。
3. **阈值告警**：面板已有 warn/bad 判定（前端），把它搬到服务端做持续 5 分钟判定 + 推送，
   才是真正解决"事后无从查证"的那一半。
4. **服务存活**：需要维护进程清单，且与 1 一起做（否则等于把内部服务拓扑公开）。
5. **迁移到 Prometheus**：一旦出现"要看 30 天"或"要看第二台机器"，就别再长这个方案了。
