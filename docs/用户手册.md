# ProcBeat 用户手册

手机浏览器点开就能看的服务器状态面板：**CPU、内存、负载、磁盘容量与磁盘 IO**，
实时值 + 7 天历史。

---

## 1. 打开面板

| 你在哪 | 地址 |
|---|---|
| 手机 / 外网 | `http://<你的公网IP>/monitor/` |
| 同 VPC 内网机器 | `http://<你的内网IP>/monitor/` |
| 就在这台服务器上 | `http://127.0.0.1:3000/`（绕过 nginx，直连 Node） |

> 手册里的地址是**占位符**。自己部署时换成实际 IP 或域名即可——
> 这份文档会随仓库公开，而面板没有鉴权（§8），真实地址不该提交进版本库。

几点注意：

- **末尾的 `/` 别丢**。`http://IP/monitor` 会 301 跳到 `/monitor/`，多数浏览器会自己跟上，
  但某些内嵌 WebView（企业微信、钉钉里直接点开）不会跟随跳转，表现就是一片空白。
- **只支持 http，没有配 https**。公网用是明文，指标数据本身不含密码之类的敏感信息，
  但别在不可信的网络里挂着它。
- **打开后 5 秒内可能是空的**。CPU 占用是两次采样求差算出来的，服务刚起来的第一个周期
  还没有基准。看到 `warming up` 或者空图，等 5 秒刷新一次就有数了。

### 装成"App"（推荐）

手机浏览器菜单里选 **添加到主屏幕**（iOS：Safari 分享按钮 → 添加到主屏幕；
Android：Chrome 右上菜单 → 添加到屏幕）。之后从图标点开是**全屏无地址栏**的独立窗口，
看起来就是个原生 App。

> 加到主屏后不会自动更新版本号——面板**没有** service worker（离线缓存），
> 所以每次打开都是服务器上的最新版，这是刻意的。

## 2. 界面一览

```
┌─────────────────────────────────────────┐
│ 服务器监控 ●           [1h][6h][24h][7d] │  ← 顶栏：实时指示灯 + 时间范围
├───────────┬───────────┬────────┬────────┤
│ CPU       │ 内存      │ 负载   │ 磁盘 / │  ← 4 张实时卡片，5 秒刷新
│ 6.4%      │ 1.10 GB   │ 0.49   │ 16.4%  │
│每核6%/8%  │共1.57GB·  │5m 0.26 │6.12 GB │
│           │可用479MB  │15m 0.18│/39.01GB│
├───────────┴───────────┴────────┴────────┤
│ CPU 占用          步长 30s · 121 点      │
│ ╱╲    ╱╲╱╲   ── CPU  ── cpu0  ── cpu1    │  ← 折线图，30 秒刷新
├──────────────────────────────────────────┤
│ 内存   ── 已用 ── 峰值 ── 可用           │
├──────────────────────────────────────────┤
│ 平均负载 ── 1min ── 5min ── 15min        │
├────────────────────┬─────────────────────┤
│ 磁盘使用率         │ 磁盘 IO              │
├────────────────────┴─────────────────────┤
│ 采样间隔 5s · 运行 128 分钟 · 最后更新 …  │  ← 底部状态行
└─────────────────────────────────────────┘
```

- **标题旁的小圆点**：绿色脉冲 = 正在实时更新；变成红色 = 最近一次拉取失败
  （网络断了、服务停了、或手机切后台太久）。底部那行会写明失败原因。
- **顶部 1h/6h/24h/7d**：只切换**历史曲线**的时间范围，实时卡片不受影响。
- **卡片上那行"每核 7% / 7%"是每根核自己的占用率**，斜杠分隔、按 cpu0 cpu1… 顺序，
  每个数自带 `%`，所以它既不是分数也不是"6 核 / 共 8 核"。两个核的数不一样通常说明
  有单线程任务压在某一核上。
- **核数超过 6 根时，这行自动换成汇总**：`每核 16 核 · 最高 100%(cpu15)`——只报核数、
  最高的那根是哪根、有多高。这不是把数据删了：逐核曲线在 **1h** 视图的 CPU 图里全都画着，
  卡片位置窄，放不下十六个数字（详见 `docs/技术方案.md` §8）。
- **百分比图（CPU、磁盘使用率）纵轴固定 0–100**，不跟着数据自动缩放。好处是小波动不会被
  拉满画幅：CPU 一直在 3% 附近抖，曲线就是贴着底边一条平线，不会看着像出了大事；
  反过来任意两天的图也能量化对比。内存、负载、IO 是绝对量，纵轴会自适应到当前范围。
- **图表标题右侧的灰色小字** `步长 30s · 121 点`：这条曲线是怎么抽稀出来的，
  点数少说明这段时间本来就没数据。
- **底部状态行**：`运行 N 分钟` 是监控进程自己的存活时长。如果你没重启过它而这里
  变成 1 分钟，说明它挂过又被 systemd 拉起来了——这本身就是有价值的信息。

## 3. 四个指标怎么读

### CPU

| 位置 | 含义 |
|---|---|
| 卡片大字 | 全部核心的平均占用率 |
| 卡片小字 | 每个核心各自的占用，`每核 6% / 8%` 表示 cpu0=6%、cpu1=8%；超过 6 核时改为只报最高的那根 |
| 图 · 蓝线 | 总占用（默认 100% 满刻度） |
| 图 · 每核线 | 只在 **1h** 视图出现。其他范围不画，因为 7 天里核数可能变化，混着画没意义 |

- **这张机器只有 2 核**，所以总量 50% 就已经相当忙了。看总量容易低估压力，
  建议主要看**每核线是不是长期贴着高值**。
- 颜色告警：**≥70% 变黄**，**≥90% 变红**。
- 这里把 `steal`（虚拟机上被宿主拿走的时间）也算成忙碌，所以极端情况下会比 `top`
  显示的值略高——那部分时间你确实干不了活。

### 内存

| 位置 | 含义 |
|---|---|
| 卡片大字 | **已用** = 物理内存总量 − 可用内存 |
| 卡片小字 | 总量与**可用** |
| 图 · 已用 | 平均已用（7 天视图里另有分钟峰值线） |
| 图 · 可用 | 内核估算的"不触发交换能腾出来的量" |

- **数字比 `free` 显示的 `used` 大，这是对的**。`free` 把可回收的页缓存算进
  `buff/cache`，但那部分随时能让给进程；面板用 `MemTotal − MemAvailable`，
  反映的是"真的占着、腾不出来"的量。
- 真正该盯的是**可用**那条线。这台机器总内存 1.6 GB：
  - 可用 **< 15%（约 240 MB）变黄**
  - 可用 **< 5%（约 80 MB）变红** —— 快到 OOM 的区间了
- 7 天/24 小时视图里的**峰值**线用来抓"平时看着没事、某个瞬间几乎打满"的情况，
  1h 视图因为是 5 秒原始点，尖峰本来就在曲线上，不再单独画峰值。

### 负载

| 位置 | 含义 |
|---|---|
| 卡片大字 | 1 分钟平均负载 |
| 卡片小字 | 5 分钟与 15 分钟 |
| 图 | 三条线：1min / 5min / 15min |

**负载 = 在跑 + 在排队等 CPU 的任务数的滑动平均**。所以：

- 负载 **对比核数**才有意义。这台机器 2 核：`1.0` 很轻松，`2.0` 饱和，`4.0` 已经在排队。
- 面板的告警线就是按核数算的：**1min 负载 > 核数 变黄，> 核数 × 1.5 变红**（即 >2 黄、>3 红）。
- **1min 高、15min 低** = 刚刚才开始忙；**三条一起高** = 已经忙了十几分钟了。
- 磁盘慢也会把负载顶高（不可中断等待算进负载），所以负载红的时候要看一眼磁盘 IO 图。

### 磁盘（容量与 IO）

| 位置 | 含义 |
|---|---|
| 卡片大字 | 根分区 `/` 使用率 |
| 卡片小字 | 已用 / 总量 |
| 图「磁盘使用率」 | 7 天趋势，看的是"什么时候会满" |
| 图「磁盘 IO」 | 读 MB/s、写 MB/s、IOPS 三条线 |

- 容量与 `df` **同口径**（预留块不算进"已用"），所以数值基本对得上；
  `df` 向上取整显示 17% 时，这里显示 16.4%。
- 告警线：**≥85% 变黄，≥95% 变红**。
- IO 统计的是**整盘设备**（`vda`），不是分区（`vda3`）。分区数据是整盘的子集，
  取分区会重复计数。
- **IO 数值为 0 不代表没在读文件**，而是"读的是页缓存，没落到盘上"。这在 Linux 上
  是常态，尤其在机器不忙的时候。要看真实读写量，得看 MB/s 那条线有没有尖峰。
- IOPS 是读次数 + 写次数。机械盘上限约 100～200，云盘看规格；这台机器的上限我没有
  官方数据，用**同时间段 IO 高点和负载高点是否重合**来判断更实用。

### 线的颜色（从上到下依次取色，每张图第一条总是蓝色）

| 图 | 蓝 | 橙 | 绿 |
|---|---|---|---|
| CPU 占用（1h） | CPU 总量 | cpu0 | cpu1 |
| CPU 占用（6h/24h/7d） | CPU 均值 | 分钟峰值 | — |
| 内存 | 已用 | 分钟峰值（仅聚合视图） | 可用 |
| 平均负载 | 1min | 5min | 15min |
| 磁盘使用率 | 使用率 | — | — |
| 磁盘 IO | 读 MB/s | 写 MB/s | IOPS |

每张图右下角的图例就是这个对应关系。深色模式下同一组颜色会自动换成更亮的色号，
顺序不变。

## 4. 时间范围与数据保留

| 范围 | 数据源 | 步长 | 大约点数 |
|---|---|---|---|
| 1h | 5 秒原始点 | 30 秒 | 121 |
| 6h | 1 分钟聚合 | 120 秒 | 181 |
| 24h | 1 分钟聚合 | 600 秒 | 145 |
| 7d | 1 分钟聚合 | 3600 秒 | 169 |

- **5 秒原始点只保留今天 + 昨天**（跨天时最多同时存在 2 个文件），
  1 分钟聚合保留 **7 天**。所以 7 天前的 5 秒级细节是看不到的——已经折叠成分钟了。
- 每条曲线最多 240 个点。手机屏幕约 400 px 宽，再密也分辨不出来，只会白耗流量。
- **曲线上出现断口** = 那段时间没有数据。可能是服务停过、机器重启过，
  或者那段历史已经被淘汰掉了。断口不要读成"指标为 0"。
- 切时间范围时曲线会立刻重取，不需要等下一个刷新周期。

### 刷新频率

| 内容 | 频率 |
|---|---|
| 4 张实时卡片 | 每 5 秒（与采样同频） |
| 5 张历史曲线 | 每 30 秒（每 6 次轮询刷一次） |
| 切到 1h/6h/24h/7d | 立刻 |

曲线之所以比卡片慢，是因为一次全刷要扫 5 个指标的日志文件，在 2 核机器上跟着
5 秒轮询跑纯属浪费。

**手机切到后台时轮询自动暂停**，回到前台会立即补一次。所以你在别的 App 里待半小时
再切回来，看到的直接就是最新值，不会显示过期数据。

## 5. 常见排查场景

### "感觉变慢了"

1. 开 **1h** 视图，看 CPU 图的每核线是不是长期贴高。
2. 若 CPU 高 → 负载同步高 → 是**算力真的不够**（有进程在吃 CPU）。
3. 若 CPU 不高但**负载高** → 十有八九是**在等磁盘或网络**，去看磁盘 IO 图的尖峰。
4. 若两者都不高 → 问题可能不在资源层（面板看不到应用内部耗时）。

### "内存会不会打满"

看**内存图的「可用」那条线**的走势，而不是当前的已用：

- 可用线**持续往下走、不回头** → 有泄漏或缓存无上限增长，会打满。趁现在还有余量，
  记下时间点去查是哪个进程。
- 可用线在低位反复震荡 → 正常，Linux 会拿空闲内存做页缓存。
- 已用线有**台阶状跳升**并且不回落 → 某个服务重启后占了更多内存，或者新起了一个服务。

### "磁盘什么时候会满"

开 **7d** 使用率图。这条线是单调往上爬的 → 线性外推到 100% 就是剩余时间。
爬升 + 回落的锯齿通常是日志轮转，不用担心。

### "夜里是不是有人在跑批"

白天正常、晚上出现 CPU/IO 尖峰 → 切 **7d** 看尖峰是否每天固定时间出现。
定时任务造成的尖峰在 7 天视图里会整齐得很容易认。

### "刚才那次卡到底是什么时候"

面板是**事后查证**的工具。切到事发时段的范围（1h 或 6h），找曲线右端那个尖峰，
它下面灰色小字里的点数与步长能帮你定位到分钟级。

## 6. 常见问题

**Q：完全打不开，浏览器说无法连接**
- 先确认服务活着：在服务器上 `bash /home/admin/workspace/monitor/monitor.sh status`
- 再确认 nginx：`curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1/monitor/` 应为 200
- 内网地址通、公网地址不通 → **云安全组没放行 80 入方向**。用
  `http://<你的公网IP>/` 试同机的其他站点首页，如果同样打不开就是安全组，与面板无关。

**Q：页面打开了，但一片空白，只有标题**
大概率是 `app.js` 没加载成功（nginx 配置改动导致）。判断方法：

```bash
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' http://127.0.0.1/monitor/app.js
```

正常必须是 `200 text/javascript; charset=utf-8`。
如果返回 `404` 或 `text/html`，说明 `/monitor/` 的 `^~` 前缀块失效了，被站点里那条
静态资源兜底正则抢走了。修法是重跑 `deploy/nginx-apply.sh`（细节见 `docs/技术方案.md` §2.3）。

**Q：卡片有数字，但图是空的**
- 底部状态行的"运行 N 分钟"若很小（1～2 分钟）：服务刚重启，历史还没积累，正常，等几分钟。
- 图标题旁灰字显示 `步长 30s · 0 点`：那个时间范围里确实没数据。切 1h 试试。
  如果那行小字一直不出现，说明这次历史请求根本没成功（`/api/history` 返回非 200），去看日志。
- 只在某个范围空白：`6h/24h/7d` 读的是聚合文件，`1h` 读原始文件，可能是聚合那条链路
  出问题了 → `bash monitor.sh logs` 看有没有 `写入失败`。

**Q：数字一直不动**
- 看圆点是不是变灰红了 → 拉取失败，底部会写原因。
- 手机浏览器后台节流：iOS Safari 和 Chrome 都会把后台页面的定时器降到每分钟一次以下。
  切回前台就会恢复。这是浏览器的行为，不是面板坏了。

**Q：为什么内存比 `free` 显示的高 / 磁盘和 `df` 差 0.6% / CPU 比 `top` 高**
都是口径差异，不是误差，见 §3 各小节。判定标准写在 `docs/技术方案.md` §4 里。

**Q：能不能看网络流量 / 哪个进程占内存最多 / 温度**
不能，这几项在需求确认时明确排除了。温度是这台机器采不到（无 `thermal_zone*`），
其余两项是当时刻意不做——理由见 `docs/技术方案.md` §1。

**Q：面板自己挂了，谁来告诉我？**
目前没有。这是"监控被监控者"的固有局限。补救办法是自己开第二个终端看：

```bash
watch -n 30 'bash /home/admin/workspace/monitor/monitor.sh status | tail -2'
```

systemd 的 `Restart=always` 会在进程崩掉后 3 秒内自动拉起，所以短暂崩一下通常
只会体现为曲线上一个小缺口和底部"运行 0 分钟"。

## 7. 运维速查

所有命令在 `/home/admin/workspace/monitor/` 下执行。已接入 systemd，日常不需要手工启动。

```bash
./monitor.sh status        # 运行状态 + 最新指标 + 数据目录占用（首选，先看这个）
./monitor.sh logs          # 最近 60 行日志
./monitor.sh logs -f       # 持续跟踪
./monitor.sh restart       # 改了 server.js / store.js 之后必须重启才生效
./monitor.sh stop          # 停（systemd 停，不会残留 nohup 进程）
./monitor.sh start         # 起
./monitor.sh selftest      # 自检：采集算法 12 项 + 前端 17 项，1 秒内跑完
./monitor.sh install       # 重装 unit 并开机自启（首次部署用的，需要 sudo）
```

### 直接问接口（脚本 / 排查用）

```bash
curl -s localhost:3000/api/current | jq
curl -s 'localhost:3000/api/history?range=6h&metric=mem' | jq '.series|map({name,n:(.points|length)})'
```

`/api/current` 的字段含义在 `docs/技术方案.md` §7；单位全是字节和毫秒，不猜。

### 看数据与资源占用

```bash
du -sh data                 # 稳态约 10 MB
systemctl show monitor.service -p MemoryCurrent,NRestarts -p MainPID
ps -o rss=,etime=,args= -p <MainPID>
ls data/raw data/agg        # 按天分文件的 JSONL，可以直接 head 看
```

`NRestarts` 是 systemd **自动**重启的次数。非 0 就说明服务崩过，去 `logs` 里找原因。

### 改配置

采样间隔、端口、数据目录都是环境变量，写在 unit 里或临时导出：

| 变量 | 默认 | 说明 |
|---|---|---|
| `MONITOR_INTERVAL` | `5000` | 采样毫秒，最小 1000。改小会让数据体积同步变大 |
| `MONITOR_PORT` | `3000` | 改这个必须同时改 `/etc/nginx/snippets/servers/monitor.conf` 里的 `proxy_pass`（改完跑 `sudo bash deploy/nginx-apply.sh` 下发） |
| `MONITOR_HOST` | `127.0.0.1` | **别改成 `0.0.0.0`** —— 面板无鉴权，对外只应经 nginx |
| `MONITOR_DATA_DIR` | `./data` | 换到大盘时记得同步 unit 里的 `ReadWritePaths` |

永久改法：`sudo systemctl edit monitor.service` 建 override，再
`sudo systemctl daemon-reload && sudo systemctl restart monitor.service`。
不要直接编辑 `/etc/systemd/system/monitor.service`（会被下次 `./monitor.sh install` 覆盖）。

### 手工跑一次（不推荐，仅作调试）

**必须清掉 `NODE_OPTIONS`**，否则本机 node 会直接拒绝启动（登录 shell 里那个
`--use-system-ca` 这个版本的 node 不认）：

```bash
cd /home/admin/workspace/monitor
NODE_OPTIONS="--max-old-space-size=96" node server.js
```

### 卸载

```bash
# 1) 删掉 drop-in 片段。站点配置里是通配 include（snippets/servers/*.conf），
#    删了文件就等于摘掉路由，不需要去动任何项目的配置，也不会把 nginx -t 弄失败
sudo rm /etc/nginx/snippets/servers/monitor.conf
sudo nginx -t && sudo systemctl reload nginx    # 确认站点没被打坏

# 2) 停服务并卸 unit
sudo systemctl disable --now monitor.service
sudo rm /etc/systemd/system/monitor.service

# 3) 数据
rm -rf /home/admin/workspace/monitor            # 历史数据一并没了
```

> 早先的布局是 `/etc/nginx/snippets/monitor.conf` + 站点里一行点名 include，
> 卸载必须**先摘 include 再删片段**，否则 nginx 会因为被点名的文件消失而 `-t` 失败。
> 2026-09-28 起改成上面的 drop-in 目录：删文件就等于摘路由，站点里那行通配 include 要留着
> （目录空着甚至整个不存在都能通过 `nginx -t`），两步之间的先后不再影响配置合法性。
> 不过还是建议**先摘路由再停服务**——反过来会让点进来的人看到 502。
> 旧布局的片段若还在，装新片段时会被挪成 `monitor.conf.removed-*` 备份。

第 3 步连历史数据一起删。想留数据就先拷走：
`cp -r /home/admin/workspace/monitor/data /somewhere/monitor-data`。

## 8. 使用前请知悉

- **面板没有鉴权**。知道地址的人就能看到这台机器的负载曲线。当前只暴露 CPU/内存/负载/磁盘，
  敏感度低；但"这台机器现在很空闲"本身也是信息。要加保护，最省事的是在
  `/etc/nginx/snippets/servers/monitor.conf` 里补 `auth_basic` + `auth_basic_user_file`
  （改完跑 `sudo bash deploy/nginx-apply.sh` 下发；仓库里的 `deploy/monitor-snippet.conf` 才是事实来源，
  别只改线上那份）。
- **只监控这台机器自身**，采的是 `/proc` 和本机 statfs，不探测任何外部服务。
- **不产生任何写入压力**（除了自己的 `data/` 目录），也不会重启或干预被监控的服务。
- 只读 `/proc`，服务以 `admin` 用户运行，因此**看不到 root 专属的信息**
  （比如别的用户进程的细节）。
- 历史数据存在本地 JSONL 里，**没有异地备份**。删掉 `data/` 就真没了。
